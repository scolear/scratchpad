Noise sunset via the topology ledger

2026-05-26

DPM stops being a messaging system and becomes a thin operator-approval shell wrapped around Canton's topology store. Same primitive handles decparty bootstrap and Decentralized Alice.

The thesis

DPM's Noise transport is doing work that Canton already does. Every Noise wire code in the current bootstrap workflow (SignDns, DnsSignature, SignP2p, P2pSignatures) maps 1:1 to operations the topology ledger already exposes: partially-signed topology proposals that propagate through the synchronizer, observed and co-signed by other participants via extendSignature. If we lean on that, Noise disappears, the workflow state machine collapses to "observe pending proposals → operator approves → extend signature," and the same architecture handles user onboarding (Decentralized Alice) without a single new DAML workflow contract.

The two corrections that collapse the design

1. The topology ledger is the coordination primitive

Calling TopologyManagerWriteService.AddTransactions with expectFullAuthorization = false puts a partially-signed topology transaction into the topology store. The proposal propagates through the synchronizer to all participants connected to it. Each participant can observe its local topology store for pending proposals and extend the signature with its own keys via extendSignature. Once the authorization threshold is reached, the proposal becomes effective. There is no need for an out-of-band channel to ferry these messages around.

The Splice codebase already does this in PartyOps.scala:197-219 for the external-party onboarding case — it's first-class Canton behavior, just under-exploited.

2. The root key cannot sign DAML — and doesn't need to

Alice's namespace root key signs topology transactions and only topology transactions. Any design that asks her to sign a DAML workflow contract before onboarding completes is broken at the chicken-and-egg level: she has no PartyToKeyMapping until onboarding finishes, so she has no key registered for ledger transactions until the very thing we're onboarding her into is already done.

This stops being a problem the moment we accept correction 1. The coordination doesn't happen in DAML; it happens in the topology ledger. Alice signs topology transactions with her root key — exactly what it's for. The rest of the workflow runs without her holding any DAML signing key.

The new layer stack

1. DpmNode registry

On-chain. Each operator publishes their participantId, namespace pubkey, signing pubkeys, public HTTP URL (for Alice's submission relay), and hosting policy. Replaces the peer-config table + "Share my data" JSON paste.

2. Topology proposals

Canton-native. Partial signatures propagate; extendSignature accumulates them; threshold trips authorization. Replaces all Noise wire codes for workflow coordination.

3. Operator UI

Driven by topology-store subscription. Pending proposal involving this participant's keys = invitation in the UI. Accept = extendSignature. Same UX, different backing store.

Alice's flow

[ Alice's wallet, offline-capable ] 1. Read GET /v0/dpm-registry from any DPM → list of candidate hosts 2. Pick N hosts whose hostingPolicy matches Alice's needs 3. Build NamespaceDelegation, PartyToKeyMapping, PartyToParticipant (multi-row) using each host's pubkeys from the registry 4. Multi-hash + sign with Alice's ROOT key 5. POST signed bundle to ANY participant's submission relay (doesn't have to be a host) [ Any relaying participant ] 6. Validates Alice's signatures 7. AddTransactions(bundle, expectFullAuthorization=false) → propagates via synchronizer [ Each chosen host's DPM, independently ] 8. Topology-store subscription fires: pending proposal references my namespace 9. Operator UI: "External user requests hosting, 2-of-3, accept?" 10. On accept: extendSignature → re-submitted with operator's sig appended [ Synchronizer ] 11. Threshold met → topology effective; Alice's party is live [ Alice's wallet — NOW she has a registered signing key ] 12. Exercises ExternalPartySetupProposal_Accept on each host (signed with the now-registered K_sign, not the root key) 13. ValidatorRight + TransferPreapproval contracts created. Done.
Note the symmetry of the topology phase: Alice's root key signs once, in the wallet. The proposal then flows through Canton's existing machinery without further intervention from her. The same is true for the operators — each clicks accept once, the rest is extendSignature bookkeeping. No state machine, no retries, no timeouts to manage.

Decparty bootstrap flow (the existing use case)

[ Operator A's DPM ] 1. Read /v0/dpm-registry to pick B and C from registered DPMs 2. Build DecentralizedNamespaceDefinition proposal: owners {A, B, C}, threshold 2 3. Sign with A's namespace key 4. AddTransactions(proposal, expectFullAuthorization=false) → propagates via synchronizer [ Operator B and C's DPMs, independently ] 5. Topology-store subscription fires: "DNS proposal naming me as owner" 6. Operator UI: "You've been proposed as a member of namespace XYZ, accept?" 7. On accept: extendSignature → re-submitted [ Synchronizer ] 8. Threshold met → DNS authorized; the decparty namespace exists [ Same machinery for PartyToParticipant of the new decparty ] 9. Similar dance for each P2P mapping. Done.

The two flows are structurally identical. The only thing that differs is whose root key signs the initial proposal and what the proposal contains. The Rust DPM service does not need to distinguish them — the same observer loop handles both.

Trust (the "network of networks" property)

Today, trust is expressed by sharing a Noise PSK out of band. Two operators with each other's PSKs can participate in workflows together. There is no explicit on-chain expression of who-trusts-whom.

After: trust is a DAML contract.

TrustEdge
  signatories: { operatorA, operatorB }   -- bilateral
  fields:
    nodeA, nodeB     : Party
    networkLabel     : Text             -- optional grouping
    purposes         : [WorkflowKind]   -- bootstrap, host-user, both
    establishedAt    : Time

The DPM UI filters pending topology proposals to ones from parties this operator has a TrustEdge with (transitively, optionally, via a TrustGroup wrapper). Untrusted proposals are visible but de-emphasized. Operators can still accept anything — the filter is a UX hint, not a security boundary. The security boundary is the operator's own signature on extendSignature.

Migration path

Phase 1 — additive. Ship the DpmNode registry contract and the /v0/dpm-registry endpoint. Keep Noise running for coordination. Decentralized Alice MVP uses the registry for discovery + submits her topology bundle via the new relay endpoint. Validates the registry shape and Alice's flow end-to-end without touching inter-DPM coordination.

Phase 2 — parallel run. Build the topology-store subscription loop and operator UI for pending proposals. Run a decparty bootstrap workflow purely via topology proposals, alongside the existing Noise-driven one. Compare behavior, fix corner cases.

Phase 3 — switchover. Make the topology-driven path the default for new bootstraps. Old workflows continue on Noise until they complete. Delete src/noise/. Delete the workflow state machine. Delete most of the SQLite schema. Net deletion: probably ~40% of the Rust codebase.

Open questions

  • Topology proposal expiry. Does Canton's topology store have native expiry for unfilled proposals? If not, stale half-signed proposals could accumulate. Worth checking before committing.
  • Cancellation. If operator A submits a DNS proposal and B accepts but C declines, what's the cleanup? Options: submit a topology Remove transaction (per Canton semantics) or just leave it un-effective with a UI marker.
  • Anti-spam. DpmNode is self-signed — any party with a Canton identity could publish one. Filter at the client (UI shows only registry entries with at least one trust edge to a known operator) or at the publication layer (a DSO-style gatekeeper for advertising).
  • Initial registry curation. Where does the very first DpmNode registry entry come from? Probably a hard-coded bootstrap list in the DPM binary, similar to validator onboarding's svClient config.

TL;DR

DPM doesn't need a transport layer. It needs an on-chain phonebook and a UI that watches the topology store. The Noise mesh, the workflow state machine, the artifact store, the peer-config table — all of that exists because Canton's topology coordination wasn't being used as the primitive it actually is. Once you adopt it, Decentralized Alice and the existing decparty bootstrap become the same primitive: signed topology proposals propagating through the synchronizer with operator approval at each participant. DPM shrinks substantially. Alice gets her flow without a single new DAML contract or signing key she doesn't already have.
