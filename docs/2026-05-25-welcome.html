Welcome to scratchpad

2026-05-25

scratchpad is a running, public collection of one-off HTML documents — reports, plans, summaries, option comparisons, design sketches — produced in the flow of work and published as a tiny static site so they can be shared with a single link.

It's deliberately minimal: no CMS, no build step, no framework. Just HTML files in a git repo, served by GitHub Pages.

Why it exists

The author often asks an AI assistant (Claude) to write up an idea, an analysis, or a set of options as an HTML document. Without a home, those docs end up scattered — in chat scrollback, in random folders, in throwaway Netlify drops. scratchpad gives them a permanent address.

  • One stable URL per doc, paste-able into Slack or email
  • One index listing everything, so old docs are still findable
  • Public, but unindexed — you need the link
  • Versioned (git), so the history of an idea is preserved

How it's structured

scratchpad/
├── index.html              ← landing page, lists every doc newest-first
├── docs/
│   ├── 2026-05-25-welcome.html
│   ├── 2026-05-25-decentralized-alice.html
│   ├── 2026-05-26-noise-sunset-via-topology-ledger.html
│   └── ...
└── README.md               ← brief notes for humans (and AIs) browsing the repo

Filename convention

YYYY-MM-DD-short-slug.html. The date prefix means files sort naturally on disk and in the file browser; the slug is a few hyphenated words capturing the topic.

Self-contained docs

Each HTML file inlines its own CSS and (where needed) JavaScript. No external assets, no shared stylesheet. This has two payoffs:

  • A doc can be downloaded and opened offline without breaking
  • Restyling the site later won't retroactively change old docs — each is frozen in the visual style it was published in

Index page

index.html is the table of contents. Each entry is a card with title, date, and a one-line description. New docs are added at the top.

Adding a doc — the workflow

When a new doc is created:

  1. The HTML is written to docs/YYYY-MM-DD-slug.html
  2. A new entry is prepended to the <ul class="docs"> in index.html
  3. The changes are committed and pushed to main
  4. GitHub Pages rebuilds the site automatically (takes ~30s)
  5. The doc is now live at its stable URL, ready to share

The author can ask Claude to do this end-to-end: "write up these tradeoffs as an HTML doc and publish it." Claude knows where the repo lives and what the conventions are because the workflow is saved in its global memory.

Sharing a doc

Every doc has a stable URL of the form:

https://scolear.github.io/scratchpad/docs/<filename>.html

Paste that into Slack, email, anywhere. Because each file is self-contained and committed to git, the URL won't rot — old docs keep working even as new ones get added and the site evolves.

The repo itself (github.com/scolear/scratchpad) is public too. Teammates who want to browse source, fork, or grep across docs can do that there.

What goes here, what doesn't

Belongs here: idea write-ups, exploration of options, summaries of long discussions, status reports, plans, design sketches — anything that's useful to share as a snapshot of thinking at a moment in time.

Doesn't belong here:

  • Project deliverables that have their own repo or wiki
  • Anything containing secrets, internal-only data, or unreleased customer info — this site is public
  • Long-lived documentation that needs ongoing maintenance — scratchpad docs are intentionally frozen; if a topic keeps evolving, give it a real home

Editing or retiring a doc

Docs are not immutable, but they're treated as snapshots. Light fixes (typos, broken links) get edited in place. When an idea is superseded, the better path is usually to write a new doc and reference the old one — that way the history of thinking is preserved. The 2026-05-26 topology-ledger doc, for instance, supersedes parts of the previous day's onboarding-options doc but doesn't replace it.
