Onboarding Decentralized Alice

2026-05-25

Three candidate flows for extending DPM (dec-party-onboarding) to support user-initiated multi-host party onboarding.

The problem in one paragraph

DPM today is a node-operator-to-node-operator choreographer: three operators each run a DPM, exchange a Noise PSK out-of-band, and jointly bootstrap a shared DecentralizedNamespaceDefinition. Decentralized Alice is shaped differently — she's an end user with a console wallet, holding her own single-owner root key, who wants three independent operators (Bitsafe, DA, PixelPlex) to host her party under Confirmation permission with a 2-of-3 threshold. There is no shared namespace, no PSK between Alice and the hosts, and no expectation that Alice runs anything node-shaped. When she clicks "onboard me as a decentralized party," what runs the workflow?

How DPM coordinates today

coordinator peer Noise transport

Steps run on a state machine: WaitingForPeers → GenerateKeys → CreateProposals → SignDns → SubmitDns → SignP2p → SubmitFinal. Each peer generates its own keys, the coordinator computes the DNS hash, everyone signs, the coordinator submits.

Three coordinator designs

A
Alice's wallet is the coordinator
most sovereign · most client logic

Alice's wallet runs the state machine. It fetches each host's policy and signing keys, builds all three topology mappings locally, signs them with her root key, and pushes the bundle to each DPM independently. Each DPM's operator approves locally, returns its co-signature on its row of PartyToParticipant, and the wallet aggregates + submits.

Pros

  • Cleanest sovereignty — no host is "first among equals"
  • Alice can abort or change her mind mid-flow with no on-chain state
  • Maps directly to the splice-wallet-kernel architecture
  • DPMs need almost no new inter-DPM messaging

Cons

  • Wallet must stay online for the whole flow (minutes — DPM has ~30s topology propagation waits)
  • Retry logic for transient host failures lives in the wallet
  • Most new code is client-side (TS / browser extension) — harder to harden
  • Wallet has to fan out N HTTP calls; UX friction grows with M

Pick this when: you want Alice's sovereignty maximized and you're already investing in the browser-extension Wallet Gateway flavor of splice-wallet-kernel.

B
One DPM coordinates on Alice's behalf
most code reuse · pragmatic MVP

Alice's wallet talks to one DPM (her choice). That DPM becomes the coordinator for this single workflow run and reuses the existing Noise channel + workflow state machine to coordinate with the other DPMs. Alice's wallet is a thin client making one HTTP call and polling for completion.

Pros

  • Massive code reuse — workflow engine, Noise transport, invitations UI, artifact store all keep working
  • Wallet UX is one button + one progress bar
  • Easier to add 3-strikes retries, resume-after-restart, operator approval
  • Inter-DPM trust already established via existing PSKs

Cons

  • Asymmetric trust — the chosen coordinator sees the request first and can stall (though not forge)
  • Need a "switch coordinator" recovery path if Bitsafe stalls; Alice retransmits to DA
  • Coordinator is a single point of liveness for this user's onboarding (until retransmit)
  • Doesn't generalize as cleanly to non-DPM hosts

Pick this when: you want to ship the MVP fastest with the least new code. Most of the work is a new workflow/tenant_onboarding/ module that mirrors the existing workflow/onboarding/ module.

C
Wallet Gateway as coordinator
ecosystem-aligned · CIP-103 native

The Wallet Gateway from the splice-wallet-kernel architecture takes the coordinator role. Alice's wallet only signs (via the CIP-103 signing channel). The Gateway fans out HTTP requests to each DPM independently — no Noise required at this layer. DPMs still talk Noise among themselves if they need to (e.g., for inter-host ACS replication), but the user-onboarding flow is gateway-mediated.

Pros

  • Aligns with the ecosystem's CIP-103 architecture out of the box
  • Decouples "who orchestrates" from "who signs" from "who hosts" — all three are pluggable
  • Gateway can be the browser extension (most sovereign) without code changes elsewhere
  • Hosts don't need new Noise message types — pure HTTP
  • Easiest to test (HTTP fixtures vs Noise harnesses)

Cons

  • Three components instead of two — more moving parts
  • If Gateway is a remote service, it's an extra trust dependency unless purely transport
  • The browser-extension Gateway is NOT IMPLEMENTED YET in splice-wallet-kernel
  • DPM's existing operator-to-operator design has to coexist with a separate user-onboarding HTTP surface

Pick this when: you're playing for the long game and want the user-onboarding shape to be ecosystem-standard rather than DPM-specific. This is also the only option where Alice can plug in a non-DPM host (any service that implements the same /tenant/* contract).

New APIs and standards needed (any option)

1. Host discovery and policy disclosure

GET /hosting-policy
→ { synchronizer_id, operator_party, willing_to_host_users: true,
    minimum_threshold, fee_schedule, sla,
    supported_token_standards, onboarding_endpoint, terms_uri }

GET /hosting-keys
→ { participant_id, daml_signing_public_key,
    namespace_fingerprint, valid_from, signed_attestation }
Required because Canton 3.4+ embeds each host's DAML signing key directly in PartyToParticipant entries. Alice's wallet (or the coordinator) can't build the proposal without reading these from each candidate host.

2. Tenant onboarding HTTP endpoints (DPM-side)

POST /tenant/onboarding-request
body: {
  namespace_delegation: <signed-tx-bytes>,
  party_to_key_mapping: <signed-tx-bytes>,
  party_to_participant: <unsigned-tx-bytes>,
  hosting_terms: { threshold, fee_commitment },
  alice_proof_of_intent: <root-key-sig-over-everything>
}
→ 202 + request_id

GET  /tenant/onboarding-request/{id}      → { status, co_signature_if_signed }
POST /tenant/onboarding-request/{id}/cancel

4. Splice DAML follow-through

After topology lands, Alice still needs to exercise ExternalPartySetupProposal_Accept to get her ValidatorRight + TransferPreapproval. Today's Splice model assumes one validator per setup proposal. With multiple hosts, design questions:

  • Three separate ExternalPartySetupProposals, one per validator? Then three accepts, three ValidatorRights.
  • Or a new MultiValidatorPartySetupProposal template with the hosts as collective signatories?
  • How does fee renewal (TransferPreapproval_Renew) distribute across multiple hosts?
This is the part where DPM extension alone is not enough — Splice's DAML layer needs an ecosystem-level standardization decision about multi-host external parties. Worth raising early.

5. Trust establishment

OptionHow Alice → DPM authn worksTradeoff
Anonymous + self-signedTLS for transport; Alice's root-key signature over the bundle is the credentialSimplest. Needs rate-limiting / payment-to-prevent-spam.
Pre-paid escrowAlice deposits hosting fee under a temporary party first; signed bundle references the escrowChicken-and-egg: needs a temp party before the main party.
KYC-attestedAlice presents a signed credential from a known issuer (e.g. OAuth IdP)Most permissioned. Compatible with existing DPM auth (Keycloak/Auth0).

Recommended path

Start with B, converge toward C.

B is the lowest-risk MVP — it adds one new tenant_onboarding workflow module to DPM and reuses everything else. It validates the user-facing flow with real operators in days, not weeks.

Once that's live, refactor the coordinator role behind a HTTP surface that's also implementable by a standalone Wallet Gateway. At that point you're effectively in C, and Alice can pick: "coordinate via Bitsafe DPM" or "coordinate via my own browser extension." Same DPM-side endpoints serve both.

Option A on its own is too much wallet code for the first iteration — but A is what C becomes if the Gateway is the browser extension.

Open questions worth your judgment

  • Is Alice anonymous or attested? Permissionless hosting needs anti-spam and a payment commitment. KYC-gated hosting needs an identity attestation. The choice affects whether the /tenant/onboarding-request endpoint is open or auth-gated.
  • One ExternalPartySetupProposal or per-validator? Touches the Splice DAML layer. Likely a new multi-validator template is needed.
  • What if one host accepts but another declines? Abort, auto-replace with another willing host, or lower the threshold? Each has UX consequences.
  • Migration vs onboarding. "Swap a host" probably uses the same flow with Alice's root key authorizing a new PartyToParticipant. DPM's existing kick workflow is close but assumes the kicker is a peer, not the party owner.
  • How does Alice discover candidate hosts? A registry contract on-ledger? A static config in the wallet? A DID-style discovery mechanism?
