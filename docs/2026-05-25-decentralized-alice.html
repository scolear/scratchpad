Decentralized Alice

2026-05-25

A sovereign Canton wallet hosted on multiple participants — Alice keeps the keys, the network keeps the uptime.

The thesis in one sentence

Alice holds her own namespace root key in her console wallet, but her on-ledger Party is hosted on a quorum of independent participant nodes (Bitsafe, DA, PixelPlex). Any 2-of-3 hosts can confirm and execute her transactions, but no host — alone or together — can move her assets, evict her, or rotate her keys without an explicit signature from Alice.

Why this is hard on most chains, and possible on Canton

Most blockchains conflate three concerns into a single private key: identity, authorization, and availability. Canton splits them into three orthogonal topology mappings:

MappingWhat it answersConcept
NamespaceDelegation Who can change Alice's identity / topology? Identity, sovereignty — the root of trust.
PartyToKeyMapping Which key signs each ledger transaction for Alice? Per-transaction authorization — the hot signing key.
PartyToParticipant Which nodes host Alice, with what permission, with what quorum? Availability, redundancy — the hosting set.

Because these are three independent records, you can mix-and-match the trust on each axis. "Self-sovereign identity + decentralized hosting + hot signing key" is just one valid configuration of the three knobs.

Two keys, two layers, two purposes

Namespace root key

Cold. Lives in Alice's console wallet (ideally hardware-backed). Signs only topology changes — onboarding, key rotation, swapping hosts. Defines Alice's namespace as Alice::<root-fp>. Never signs a transfer.

External signing key

Hot. Also in Alice's wallet. Signs the hash of every prepared ledger transaction. Its authority exists only because the root key published a PartyToKeyMapping binding it to Alice's Party. Rotatable cheaply.

Host node keys

Held by Bitsafe / DA / PixelPlex. Sign their own confirmation messages and topology co-signatures. Do not have authority to sign on Alice's behalf. Validators + submitters, not custodians.

The cryptographic chain (per transaction)

root key ──signs once──▶ PartyToKeyMapping { party: Alice, keys: [ext_sig_key] } │ ▼ ext_sig_key ──signs each tx hash──▶ TransferInstruction request │ ▼ Bitsafe / DA / PixelPlex (verify ext_sig_key against PartyToKeyMapping, walk NamespaceDelegation, check root fingerprint) │ ▼ 2-of-3 confirmations ──▶ Mediator ──▶ Sequencer ──▶ ledger updated

Onboarding — what the root key signs (once)

The console wallet builds three topology transactions, Alice's root key signs them in a combined multi-hash, hosts co-sign the PartyToParticipant, and the bundle is submitted:

MappingWhat it assertsSigned by
NamespaceDelegation "This root key owns the namespace Alice::<fp>." Root key (Alice)
PartyToKeyMapping "This signing key represents Alice for ledger transactions." Root key (Alice)
PartyToParticipant "Bitsafe, DA, PixelPlex host Alice with Confirmation permission, threshold 2-of-3." Root key (Alice) + each host's key

On-ledger, Alice also exercises ExternalPartySetupProposal_Accept, producing a ValidatorRight and a TransferPreapproval (inbound receipts + automated holding-fee renewal). After this, the root key goes cold.

Per-transfer flow — "Alice sends 10 Amulets to Bob"

[1] Wallet prepares command on Bitsafe → returns serialized prepared tx + hash Token Standard transfer → AmuletTransferInstruction(sender=Alice, receiver=Bob, amount=10) [2] Wallet independently recomputes the hash and verifies it matches (trust-no-single-host hygiene) [3] Alice signs the hash locally with her external signing key (root key untouched) [4] Wallet submits (prepared_tx + signature) to Bitsafe → broadcast to DA + PixelPlex Each host verifies signature against Alice's PartyToKeyMapping in topology [5] 2-of-3 confirmations reach the Mediator → Sequencer timestamps On-ledger result: an AmuletTransferInstruction contract (Alice's signed commitment, amulets locked pending receiver acceptance) [6] Bob exercises TransferInstruction_Accept (or _Reject, or Alice _Withdraws, or expiry _Update) Unlocks the locked amulet, creates Bob's output Re-confirmed by Alice's 2-of-3 quorum [7] Final state: Alice -10 -fees, Bob +10, AmuletTransferInstruction archived
The AmuletTransferInstruction created in step 5 is the on-ledger "delegation contract" referenced in the abstract: a concrete, ledger-visible, single-shot authorization Alice externally signed via the Token Standard interface. It decouples "Alice's commitment to send X to Y" from "settlement" — the locked amulets sit there until the receiver accepts, the sender withdraws, or the deadline expires.

OperationRequires Alice's signature?Why
Outbound transferYes — external signing key per txValue-moving; Alice's explicit intent.
Holding-fee renewalNoTransferPreapproval_Renew burns input amulets automatically; controller is the host, not Alice.
Holdings mergeNoMergeDelegation_Merge consolidates fragmented holdings; gas optimization.
Inbound transfer (someone pays Alice)NoTransferPreapproval_Send lets the sender authorize.

Loss and rotation semantics

ScenarioOutcomeRecovery
External signing key stolen recoverable Root key publishes a new PartyToKeyMapping replacing the compromised key. Old signatures fail verification.
External signing key lost recoverable Same — root mints a new mapping for a fresh key.
One host offline no impact 2-of-3 quorum still reachable.
Two hosts offline transfers halt Alice uses root key to publish a new PartyToParticipant with replacement hosts.
Root key stolen catastrophic None — the root key is the identity. Thief can rotate everything. Cold storage is non-negotiable.
Root key lost bricked Party frozen in current topology. Outbound transfers work until signing key needs rotation; then unusable.

Properties achieved

Sovereignty

Only Alice's root key can authorize identity, key, or hosting changes. No host or quorum can evict her or impersonate her.

Redundancy

2-of-3 quorum tolerates one host failure with zero impact. Two failures freeze transfers but never destroy state — Alice migrates with her root key.

Operational ergonomics

Routine work (fee renewal, holding merges, inbound payments) runs without Alice's signature. Each automation is gated by an on-ledger contract she authorized.

Privacy

Hosts see only the sub-transaction views they need to validate. The dApp never sees Alice's keys; the gateway routes signing requests to whatever custody Alice picked.

Key hygiene

Root and signing keys are separate mappings. Root stays cold. Signing key is hot and rotatable. Compromise of the hot key is not a catastrophic event.

Trust-minimized hosting

Hosts hold Confirmation (not Submission) permission. They cannot submit on Alice's behalf without her per-transaction signature. The 2-of-3 is a quorum of witnesses, not custodians.

Where the tooling stands today

The Canton + Splice server side is fully wired: generateExternalPartyTopology builds the three mappings; allocateExternalParty ingests them; TransferPreapproval / AmuletTransferInstruction (Token Standard) / ValidatorRight / MergeDelegation compose the DAML-level delegation semantics. The DSO itself is built on the same DecentralizedNamespaceDefinition primitive that could (separately) be used to share namespace ownership.

The client side — splice-wallet-kernel — implements the corresponding TypeScript Wallet SDK, dApp SDK, and Wallet Gateway. It exposes PartyMode.EXTERNAL with pluggable signing drivers (internal, Fireblocks, Blockdaemon, participant). The multi-hosting workflow is documented and demonstrated in examples/scripts/03-parties.ts.

Two gaps relative to the design above:
  • The browser-extension Wallet Gateway (wallet-gateway-extension) — the cleanest realization of "console wallet, keys never leave the browser" — is currently marked NOT IMPLEMENTED YET. The available wallet-gateway-remote is a server Alice must trust.
  • The SDK's createKeyPair generates one Ed25519 keypair and reuses it for both NamespaceDelegation and PartyToKeyMapping. The primitives support splitting them, but ergonomic helpers for "cold root + hot rotatable signer" are still DIY.

TL;DR

Canton's three-mapping topology lets you independently choose who owns the identity, which key signs each transaction, and which nodes host the data. Decentralized Alice picks: Alice owns identity (cold root key), Alice signs every tx (hot external key), three independent hosts run the infrastructure with 2-of-3 confirmation. The result is a wallet that is self-sovereign, redundant, hot-rotatable, and operationally lazy — without needing a custodian or a multisig at any layer.
