Decentralized Alice

2026-05-25

A sovereign Canton wallet hosted on multiple participants — Alice keeps the keys, the network keeps the uptime.

The thesis in one sentence

Alice holds her own namespace root key in her console wallet, but her on-ledger Party is hosted on a quorum of independent participant nodes (Bitsafe, DA, PixelPlex). Any 2-of-3 hosts can confirm and execute her transactions, but no host — alone or together — can move her assets, evict her, or rotate her keys without an explicit signature from Alice.

Why this is hard on most chains, and possible on Canton

Most blockchains conflate three concerns into a single private key: identity, authorization, and availability. Canton splits them into three orthogonal topology mappings:

MappingWhat it answersConcept
NamespaceDelegation Who can change Alice's identity / topology? Identity, sovereignty — the root of trust.
PartyToKeyMapping Which key signs each ledger transaction for Alice? Per-transaction authorization — the hot signing key.
PartyToParticipant Which nodes host Alice, with what permission, with what quorum? Availability, redundancy — the hosting set.

Because these are three independent records, you can mix-and-match the trust on each axis. "Self-sovereign identity + decentralized hosting + hot signing key" is just one valid configuration of the three knobs.

Alice's key

One Ed25519 keypair in Alice's console wallet does both jobs that Canton models as separate: it owns her namespace (signs topology) and it's the registered signing key (signs every ledger transaction). The two-mapping split (NamespaceDelegation + PartyToKeyMapping) allows these to be different keys but doesn't require it. Same UX as a typical blockchain wallet.

Alice's key

One Ed25519 keypair, in the console wallet. Signs topology transactions at onboarding and during key/host changes; signs every ledger transaction in between (e.g. AmuletTransferInstruction). Loss or theft is total — see the table below.

Host node keys

Held by Bitsafe / DA / PixelPlex. Sign their own confirmation messages and topology co-signatures. Do not have authority to sign on Alice's behalf. Validators + submitters, not custodians.

Future option: split Alice's key into a cold namespace root (signs only topology, rarely used) and a hot signing key (signs every transaction, rotatable). Canton supports this directly — PartyToKeyMapping can reference a different key from the one in NamespaceDelegation. Gains rotation and cold-storage protection; costs UX. Worth it for higher-assurance setups; deferred for the MVP.

The cryptographic chain (per transaction)

Alice's key ──signs at setup──▶ NamespaceDelegation + PartyToKeyMapping + PartyToParticipant (defines Alice::, binds key to party, places party on hosts) Alice's key ──signs each tx hash──▶ AmuletTransferInstruction (or any ledger exercise) │ ▼ Bitsafe / DA / PixelPlex (verify signature against PartyToKeyMapping, walk NamespaceDelegation, check fingerprint) │ ▼ 2-of-3 confirmations ──▶ Mediator ──▶ Sequencer ──▶ ledger updated

Onboarding — what Alice signs (once)

The console wallet builds three topology transactions, Alice signs them in a combined multi-hash with her key, hosts co-sign the PartyToParticipant, and the bundle is submitted:

MappingWhat it assertsSigned by
NamespaceDelegation "This root key owns the namespace Alice::<fp>." Alice
PartyToKeyMapping "This signing key represents Alice for ledger transactions." Alice
PartyToParticipant "Bitsafe, DA, PixelPlex host Alice with Confirmation permission, threshold 2-of-3." Alice + each host's key

On-ledger, Alice also exercises ExternalPartySetupProposal_Accept, producing a ValidatorRight and a TransferPreapproval (inbound receipts + automated holding-fee renewal). After this, Alice's key is only needed for transfers and the occasional topology change.

Per-transfer flow — "Alice sends 10 Amulets to Bob"

[1] Wallet prepares command on Bitsafe → returns serialized prepared tx + hash Token Standard transfer → AmuletTransferInstruction(sender=Alice, receiver=Bob, amount=10) [2] Wallet independently recomputes the hash and verifies it matches (trust-no-single-host hygiene) [3] Alice signs the hash locally with her key [4] Wallet submits (prepared_tx + signature) to Bitsafe → broadcast to DA + PixelPlex Each host verifies signature against Alice's PartyToKeyMapping in topology [5] 2-of-3 confirmations reach the Mediator → Sequencer timestamps On-ledger result: an AmuletTransferInstruction contract (Alice's signed commitment, amulets locked pending receiver acceptance) [6] Bob exercises TransferInstruction_Accept (or _Reject, or Alice _Withdraws, or expiry _Update) Unlocks the locked amulet, creates Bob's output Re-confirmed by Alice's 2-of-3 quorum [7] Final state: Alice -10 -fees, Bob +10, AmuletTransferInstruction archived
The AmuletTransferInstruction created in step 5 is the on-ledger "delegation contract" referenced in the abstract: a concrete, ledger-visible, single-shot authorization Alice externally signed via the Token Standard interface. It decouples "Alice's commitment to send X to Y" from "settlement" — the locked amulets sit there until the receiver accepts, the sender withdraws, or the deadline expires.

What's delegated to the hosts (and what isn't)

OperationRequires Alice's signature?Why
Outbound transferYesValue-moving; Alice's explicit intent on each ledger transaction.
Holding-fee renewalNoTransferPreapproval_Renew burns input amulets automatically; controller is the host, not Alice.
Holdings mergeNoMergeDelegation_Merge consolidates fragmented holdings; gas optimization.
Inbound transfer (someone pays Alice)NoTransferPreapproval_Send lets the sender authorize.
Rotate key (whole identity)Yes — effectively a re-onboardingSingle-key model: the key is the namespace fingerprint, so rotating changes Alice's party ID. The future two-key split makes routine rotation possible without identity churn.
Add/remove a hostYes — Alice + new hostTopology change to PartyToParticipant.
Migrate to entirely new hostsYesAlice cannot be evicted; she can always leave.

Loss and rotation semantics

ScenarioOutcomeRecovery
Alice's key stolen catastrophic None — the key is the identity. Thief can re-host, rotate, drain, impersonate. Backup hygiene (seed phrase, hardware wallet) is non-negotiable.
Alice's key lost bricked Party frozen in current topology. Inbound transfers via TransferPreapproval still land; outbound and topology changes do not.
One host offline no impact 2-of-3 quorum still reachable.
Two hosts offline transfers halt Alice signs a new PartyToParticipant with replacement hosts (2-of-3 of the new set required to authorize).
The future two-key split would split the top two rows: signing-key compromise becomes recoverable (root republishes PartyToKeyMapping with a fresh key); only root-key compromise stays catastrophic. Same Canton primitives, more granular failure modes.

Properties achieved

Sovereignty

Only Alice can authorize identity, key, or hosting changes. No host or quorum can evict her or impersonate her.

Redundancy

2-of-3 quorum tolerates one host failure with zero impact. Two failures freeze transfers but never destroy state — Alice migrates with her key.

Operational ergonomics

Routine work (fee renewal, holding merges, inbound payments) runs without Alice's signature. Each automation is gated by an on-ledger contract she authorized.

Privacy

Hosts see only the sub-transaction views they need to validate. The dApp never sees Alice's keys; the gateway routes signing requests to whatever custody Alice picked.

Simple key management

One Ed25519 keypair in the console wallet handles both topology and transactions — same model as a typical blockchain wallet. Splitting into cold root + hot signing key is supported by Canton and worth the UX cost for higher-assurance setups; deferred for the MVP.

Trust-minimized hosting

Hosts hold Confirmation (not Submission) permission. They cannot submit on Alice's behalf without her per-transaction signature. The 2-of-3 is a quorum of witnesses, not custodians.

Where the tooling stands today

The Canton + Splice server side is fully wired: generateExternalPartyTopology builds the three mappings; allocateExternalParty ingests them; TransferPreapproval / AmuletTransferInstruction (Token Standard) / ValidatorRight / MergeDelegation compose the DAML-level delegation semantics. The DSO itself is built on the same DecentralizedNamespaceDefinition primitive that could (separately) be used to share namespace ownership.

The client side — splice-wallet-kernel — implements the corresponding TypeScript Wallet SDK, dApp SDK, and Wallet Gateway. It exposes PartyMode.EXTERNAL with pluggable signing drivers (internal, Fireblocks, Blockdaemon, participant). The multi-hosting workflow is documented and demonstrated in examples/scripts/03-parties.ts.

Gap relative to the design above: the browser-extension Wallet Gateway (wallet-gateway-extension) — the cleanest realization of "console wallet, keys never leave the browser" — is currently marked NOT IMPLEMENTED YET. The available wallet-gateway-remote is a server Alice must trust.

TL;DR

Canton's three-mapping topology lets you independently choose who owns the identity, which key signs each transaction, and which nodes host the data. Decentralized Alice picks: one Ed25519 key in the console wallet handles both identity and transactions, three independent hosts run the infrastructure with 2-of-3 confirmation. The result is a wallet that is self-sovereign, redundant, and operationally lazy — with the same UX as a normal blockchain wallet, no custodian, no multisig. Splitting the key into cold root + hot signing key is supported but deferred.
